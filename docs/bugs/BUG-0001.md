# BUG-0001: `--lb-range` 在恢复/配置文件场景被过早约束校验误拒绝

> 模块: cli | 严重度: medium | 状态: resolved
> 发现日期: 2026-03-05 | 关联 Commit: `-`
> 关联日志: [2026-03-05](../work-journal/2026-03-05.md)

## 1 现象

- 当用户传入 `--lb-range`，但 `--lb` flag 为空时，CLI 在命令早期直接报错。
- 即便集群配置（恢复场景）或配置文件中已声明 `loadbalancer: metallb`，仍会被误判为非法组合。
- 影响 `up` 命令在恢复语义下使用 `--lb-range` 的可用性。

## 2 诊断过程

### 假设 1：约束规则本身错误
- 验证方法：检查 `validateLBRangeConstraint` 规则定义与计划文档约束。
- 结果：排除。规则本身正确（`--lb-range` 仅应与有效的 `metallb` 组合）。

### 假设 2：约束校验时机错误
- 验证方法：检查 `cmd/ohmykube/app/up.go` 执行顺序，确认是否在加载 cluster/config 前就执行校验。
- 结果：确认。校验发生在读取并合并已有 cluster 配置之前，导致无法基于“最终有效 LB”判断。

## 3 根因分析

- 根因是 `--lb-range` 约束校验执行过早，使用了未完成解析的 flag 值。
- 涉及代码路径：`cmd/ohmykube/app/up.go`（`RunE` 中校验位置；`validateLBRangeConstraint` 调用）。
- 之前未发现原因：现有测试覆盖了纯 flag 组合，但未覆盖“flag 为空 + cluster/config 已声明 metallb”的恢复语义场景。

## 4 修复方案

- 选择方案：将约束校验移动到 cluster/config 解析之后，基于“有效 LB 来源”做判断。
- 关键改动：
  - 新增 `effectiveLBForRangeValidation(flagLB, cls)` 计算最终用于校验的 LB。
  - 新增 `validateLBRangeConstraintWith(lbType, addrRange)`，并保留原函数作为包装。
  - 增补对应回归测试覆盖恢复语义。
- 放弃方案：继续沿用早期校验并在异常场景特判，复杂度更高且可读性较差。
- 修改文件：
  - `cmd/ohmykube/app/up.go`
  - `cmd/ohmykube/app/up_test.go`

## 5 验证

- 聚焦测试：
  - `go test ./cmd/ohmykube/app/... -run 'TestEffectiveLBForRangeValidation|TestValidateLBRangeConstraint_EffectiveLB' -count=1`
- 回归测试：
  - `go build ./...`
  - `go test ./pkg/config/...`
  - `go test ./pkg/addons/...`
  - `go test ./cmd/ohmykube/app/...`

## 6 经验教训

- 约束类校验应基于“最终生效配置”而非早期输入片段，尤其是存在恢复态/配置文件覆盖的命令流。
- 对 CLI 约束测试应补充“多输入源合并后的语义校验”用例。
