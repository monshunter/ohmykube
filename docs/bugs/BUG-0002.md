# BUG-0002: Lima managed 与 unmanaged `socket_vmnet` 模式冲突导致集群网络不可达

> 模块: provider | 严重度: high | 状态: resolved
> 发现日期: 2026-08-12 | 关联 Commit: `fix(provider): use unmanaged socket_vmnet network (BUG-0002)`
> 关联日志: `-`

## 1 现象

- `ohmykube up` 创建 VM 时可能报错 `network "shared" is not defined`。
- 补齐 Lima 的 `shared` 网络定义后，集群创建流程会报告成功，但宿主机访问 kube-apiserver IP 时返回 `host is down`。
- VM 内部 kube-apiserver 正常运行，宿主机上的 kubeconfig 无法访问控制面，集群实际不可用。

## 2 诊断过程

### 假设 1：Ohmykube 专用 Lima 目录缺少 `shared` 网络定义

- 验证方法：检查 `$LIMA_HOME/_config/networks.yaml` 和 `limactl network list`。
- 结果：确认初始配置只包含 `user-v2`，这是首次创建失败的直接原因；但恢复默认 `shared` 定义后，宿主机到 VM 的数据面仍不可达。

### 假设 2：kube-apiserver 或 Kubernetes 节点尚未完成初始化

- 验证方法：通过 `limactl shell` 在控制面 VM 内检查 kube-apiserver 容器，并访问本机 `/livez`。
- 结果：排除。kube-apiserver 容器处于 Running，VM 内 `/livez` 返回 `ok`。

### 假设 3：两个 `socket_vmnet` 进程竞争同一个 shared 网段

- 验证方法：检查系统进程、LaunchDaemon、Lima `_networks` 日志、宿主机路由和 ARP 状态。
- 结果：确认。系统已有 unmanaged `/var/run/socket_vmnet` 守护进程，Lima 又尝试为 `lima:shared` 启动 managed 守护进程；后者日志出现 `pidfile_open: Resource temporarily unavailable`，VM 获得地址但宿主机数据面不可达。

## 3 根因分析

- `pkg/provider/lima/lima.go` 对 `socket_vmnet` 采用了互相矛盾的所有权模型：Provider 初始化时要求外部守护进程已经运行，创建 VM 时却配置 `{"lima": "shared"}`，要求 Lima 再管理一个 shared 守护进程。
- 当专用 `networks.yaml` 不包含 `shared` 时，Lima 在创建 VM 前失败；当 `shared` 存在时，managed 守护进程又会与现有 unmanaged 守护进程竞争同一网络资源。
- 原测试只检查进程是否存在和 `LIMA_HOME` 是否设置，没有验证 VM 启动网络表达式与守护进程所有权是否一致。

## 4 修复方案

- 保留项目当前由系统 LaunchDaemon 提供的 unmanaged `/var/run/socket_vmnet` 所有权。
- 将 VM 第二张网卡从 `{"lima": "shared"}` 改为 `{"socket": "/var/run/socket_vmnet"}`，继续保留 `user-v2` 作为 VM 间网络。
- 增加回归测试，约束 VM 网络必须使用 unmanaged socket，且不能再次引用 managed `lima:shared`。
- 同时移除 shell 中全局导出的 `LIMA_HOME`，重新生成 Ohmykube 专用 Lima 网络配置，防止 Colima 再次覆盖该目录。
- 未选择停用系统 LaunchDaemon 并改由 Lima managed 网络接管，因为这会改变现有 daemon 所有权并影响其他可能使用 `/var/run/socket_vmnet` 的本机调用方。
- 修改文件：
  - `pkg/provider/lima/lima.go`
  - `pkg/provider/lima/lima_test.go`

## 5 验证

- 聚焦测试：`go test ./pkg/provider/lima -count=1`
- 全量回归：`go test ./...`
- 安装验证：`make install` 后执行 `ohmykube up`，集群在 1 分 13 秒内创建成功。
- 运行时验证：
  - 3 台 Lima VM 均为 `Running`，且只存在一个 unmanaged `socket_vmnet` 进程。
  - 3 个 Kubernetes Node 均达到 `Ready`。
  - kube-system、kube-flannel、local-path-storage 的全部 Pod 均达到 `Running` / Ready。
  - 宿主机 `kubectl cluster-info` 可访问控制面，`/readyz` 与 `/livez` 均返回 `ok`。

## 6 经验教训

- 使用外部守护进程的 Provider 配置必须统一资源所有权：启动前检查、VM 网络声明和清理行为应全部采用 managed 或全部采用 unmanaged，不能混用。
- VM 创建成功或 kubeadm 执行成功不能证明宿主机数据面可用；本地集群验收必须从宿主机验证 kube-apiserver、Node Ready 和系统 Pod Ready。
- 对生成型 VM 配置应增加契约测试，防止依赖检查与最终下发配置发生语义漂移。
